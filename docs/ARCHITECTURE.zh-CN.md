# 架构

English: [ARCHITECTURE.md](ARCHITECTURE.md)。

## crate 划分

```
rust-airplay-cli          命令行接收端
        |
        v
rust-airplay              库
  receiver                会话：套接字、发现、密钥、流
  server                  TCP 上的控制协议
  media                   音频、镜像、时序、数据报套接字
  discovery               mDNS 记录
  pairing、srp、crypto、fairplay、plist、wire
  render                  渲染器边界
        ^
        |
rust-airplay-gstreamer    一个渲染器
```

箭头表示"依赖"。库不依赖本仓库内任何其他 crate，这正是整个工作区能在没有媒体库的机器上构建的原因。后端依赖库与 GStreamer。程序依赖库，在启用 `gst` 特性时还依赖后端。

## 一次会话是什么样子

客户端通过 mDNS 找到接收端，向控制端口建立 TCP 连接，在上面说 RTSP。

1. `GET /info` 返回与广播相同的文本记录，因此客户端无论从哪边读到，看到的都是同一份广播。
2. `POST /pair-verify` 证明客户端持有它配对时得到的密钥。从未配对过的客户端走 `POST /pair-setup`，在那里 SRP 交换加上屏幕上的 PIN 证明用户就在设备旁边。
3. `POST /fp-setup` 是投屏客户端在发送加密视频之前要求的 FairPlay 握手。
4. `SETUP` 声明流。应答里带着接收端绑定的端口，请求里带着会话要用的密钥。
5. `RECORD` 开始播放。媒体随后从时序、控制、数据三个套接字到达，镜像画面从镜像监听到达。
6. `TEARDOWN`，或连接关闭，结束会话。

音频密钥与镜像标识正是会话要跨连接共享的原因。客户端在某次 `SETUP` 里发送音频密钥，之后的另一次 `SETUP` 里发送镜像流的 `streamConnectionID`，且不重复密钥。由于接收端按连接构建设置处理器集，按连接保存的状态会把密钥丢掉；因此密钥属于会话。

## 接收媒体

音频以 RTP over UDP 到达，每个包用 AES-CBC 解密（每条包重置），随后进入有界重排窗口。当序号缺失、而客户端当初声明过重传时，接收端会在控制套接字上请求补发；正是这个请求把丢包变成了可恢复。帧按序离开窗口；补不上的缺口被计数并跳过，少一个包的流仍继续播放。

镜像从 TCP 到达，包带 128 字节包头。一个包的密钥流是流上 key 与 IV 的 AES-CTR，而"字节从哪里取"是微妙之处：它从上一个包结束的地方开始，按整块读。长度不满最后一块的包会把该块的剩余字节留给下一个包，而这些字节在流里根本不存在，因为它们属于一块已经被读过的地方。计数器随后按该包自身字节填满的块数前进。这条规则是拿 UxPlay 的实现比对出来的，而不是推导出来的；那条测试也是这里能写得这么具体的原因。

帧以 Annex-B 访问单元的形式离开媒体路径。单独发送参数集的客户端，其参数集会被拼到所属帧之前。

## 渲染

帧以带时间戳的独立缓冲区跨过 trait 边界。接收循环绝不能等渲染器，因此每个流都由自己的线程写入，由有界队列供给。队列满时丢弃最旧的一帧，滞后因此被限制在队列深度内而不会增长；画面可能到下一个关键帧之前都不完整，会话会把这件事写进日志。

GStreamer 后端必须用两种方式投递两种媒体，原因在格式本身。H.264 带起始码，解码器能在字节流里找到画面边界，这正是 `gst-launch-1.0` 子进程从标准输入拿到的东西。raw AAC-ELD 帧既没有同步字也没有采样率，字节流说不出帧到哪里结束；唯一可行的投递方式是一帧一 buffer 走 `appsrc`，而这需要链接 `libgstreamer`。这就是后端作为独立 crate、需要 GStreamer 开发库，而默认工作区不链接任何东西的原因。

## 发现

接收端同时注册 `_raop._tcp` 与 `_airplay._tcp`，并把当前客户端会读的文本记录填好。这些值不是装饰：例如 feature 位图的第 27 位决定客户端使用哪套配对协议。测试逐字段钉住了这些值，且它们取自运行中的接收端而不是头文件：头文件记录的是构建初值，程序在广播前可能改变它。

## 身份

身份是 32 字节种子。设备标识与会话使用的密钥都由它派生，因此一个种子就是一个接收端；配对过的客户端在重启后仍能认出它。客户端密钥在会话携带过它之后才被记住，这是诚实的边界：从未完成会话的客户端还没有证明任何事情。

库既不保存种子，也不保存客户端列表。持久化它们的程序让接收端可被认出；不持久化的程序得到的接收端每次都像是新的，对于一个不该记住任何东西的接收端来说，这是合理的选择。
