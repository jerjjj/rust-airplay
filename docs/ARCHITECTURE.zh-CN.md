# 架构

English: [ARCHITECTURE.md](ARCHITECTURE.md)。

本文说明各部分如何协作，以及为什么这样拆分。它取代了项目早先保留的决策记录，那些决策连同理由在这里重述。

## 结构

```
rust-airplay-cli          程序：参数、文件、打印
        |
        v
rust-airplay              库
  +-- receiver            会话：端口、发现、密钥、流
  +-- server              TCP 上的控制协议
  +-- media               音频、镜像、时序、数据报套接字
  +-- discovery           mDNS 广播
  +-- pairing、srp、crypto、fairplay、plist、wire
  +-- render              渲染器接入的边界
        ^
        |
rust-airplay-gstreamer    渲染器：音频进程内，视频子进程
```

箭头表示"依赖"。库不依赖本仓库内任何其他 crate；后端依赖库与 GStreamer；程序依赖库，以及可选的 backend。

## 边界为什么在这里

"用什么播放"不该由协议那半边决定：走 GStreamer、走别的、还是什么都不播。因此库只带一组很小的 trait——`Renderer`、`AudioStream`、`VideoStream`——把帧递过去。现有两个实现：全部接受但不播放的 `NullRenderer`，以及 GStreamer 后端。

trait 刻意做得很薄。帧以带时间戳的独立缓冲区跨过边界：会话无法把内存借给一个它不控制的后端，而且会阻塞接收循环的后端会拖住循环关注的一切。写操作在后端吃不下时**应当阻塞**；接收循环从不直接写。这正是"有声会话卡死"曾经的原因，而现在它是设计上的性质，不是某一个后端的行为。

## 命令行为什么这么薄

凡是能做成值的东西都做成值：身份种子、客户端集合、轨迹文件、渲染器。库不读环境变量、不选路径、不打印。嵌入它的程序保留这些决定，库本身保持可测——测试可以用 `[0x42; 32]` 的身份和"只数帧"的渲染器跑完整个会话。

库唯一自己管的是停止信号：`run` 会监听进程被中断，因为活得比它更久的接收循环会占着声卡却无物可播。想换触发方式的调用方丢弃这个 future 即可。

## 协议路径

客户端通过 mDNS 找到接收端，建立 TCP 连接，在上面说 RTSP。

| 步骤 | 发生什么 |
|---|---|
| `/info` | 用与广播相同的文本记录应答 |
| `/pair-verify` | Curve25519，已配对客户端无需 PIN 即被认出 |
| `/pair-setup` | SRP-6a + PIN，用于尚未被信任的客户端 |
| `/fp-setup` | 投屏客户端期望的 FairPlay 握手 |
| `SETUP` | 客户端声明它的流；接收端应答实际绑定的端口 |
| `RECORD` | 开始播放 |
| `SET_PARAMETER` | 音量、进度、元数据 |

`SETUP` 藏着大部分有意思的工作。客户端在其中发送音频密钥，而在**后来的**一次 `SETUP` 里发送镜像流的连接标识，且不重复密钥。这两次未必来自同一条连接，因为接收端按连接构建设置处理器集。因此音频密钥是**会话状态**而非连接状态，在处理器集之间共享。

## 媒体路径

三个数据报套接字承载媒体：时序、控制、数据。第四个是 TCP 监听，承载镜像画面。

**音频**走 RTP，用 AES-CBC 解密（每条包重置），进入有界重排窗口。迟迟不到的包会在控制套接字上请求重传，重传正是让缺口可恢复的手段。帧按序离开窗口；补不上的缺口被计数并跳过，而不是让整条流停住。

**镜像**走 TCP，包带 128 字节包头。密钥流由流的 key 与 IV 派生，而"一个包的字节从哪里读"并不是显而易见的规则：一个包从**上一个包结束的地方**开始读，按整块读，所以长度不满一块的包会把该块剩余的字节留给下一个包——而这些字节**不在流里**，因为它们属于一块已经被读过的数据。计数器随后按该包**新读的字节**所占块数前进。这条规则是拿 UxPlay 自身的代码测出来的，不是推导出来的；那条测试也是这段话能说得这么具体的原因。

**帧**以 Annex-B 访问单元的形式离开这条路径。客户端单独发送的参数集会拼到它所属的帧之前。

## 为什么用 GStreamer，为什么是两种形态

播放媒体需要本项目不打算自己实现的解码器。选 GStreamer 是因为 UxPlay 用它，这样行为可对比，出错也容易辨认。

两种媒体的投递方式不同，这不是偏好问题：

- **视频是子进程**。H.264 与 H.265 带起始码，解码器能在字节流里找到画面边界。启动 `gst-launch-1.0`，把帧写进它的标准输入即可。
- **音频是链接的**。raw AAC-ELD 帧没有同步字、也没有采样率，字节流说不出"一帧到哪里结束"。唯一可行的投递方式是一帧一 buffer，也就是 `appsrc`，也就是链接 `libgstreamer`。

代价是这个 crate 构建期需要 GStreamer 开发库——这正是它被拆成独立 crate、而默认 workspace 完全不链接 C 库的原因。

## 一次会话的开销，以及时间花在哪

在开发机上用仓库内的真机会话数据测得：

| 项目 | 开销 |
|---|---|
| 控制面单个请求 | 一毫秒以内 |
| 接收端握手（首条请求到首帧） | 约 340 ms |
| 视频 sink 起来（还未收到任何帧） | 约 700 ms |
| 解码 30 帧真机 1554x1080 到文件 sink | 354 ms |
| 同样内容到窗口 sink | 1100 至 1750 ms，取决于 sink |

sink 就是"连接感觉慢"的原因，也是后端允许视频管线随接收端一起启动（`AIRPLAY_GST_VIDEO_WARM`）而不是等第一个客户端的原因：窗口是在管线启动时创建的，不是画面到达时。

## 广播内容是一份契约

接收端的 mDNS 文本记录决定客户端如何连接，而其中一个字段起的作用远超其他：feature 位图的**第 27 位**决定用哪套客户端配对协议。置位，客户端走旧流程；清零，走现在的流程。本项目最初把这个常量从 UxPlay 的头文件里抄了过来——那是**构建初值**，UxPlay 在广播前用代码把这一位清掉，运行中的接收端报出的数字与头文件并不相同。

这条教训写在这里，因为它是本项目里代价最大的一段弯路：**读运行中的接收端，而不是读头文件里的常量**。本移植现在广播的值与运行中的 UxPlay 1.74 逐字段一致，并有测试钉住。

## 身份

接收端的身份是 32 字节种子。设备标识由它派生，所以一个种子就是一个接收端，重启后仍是同一个，配对过的客户端能认出它。客户端密钥只在**会话携带过它之后**才被记住：从未完成会话的客户端还不算已知，这是"只记住已验证密钥"的诚实边界。

库不保存种子。忘了保存种子的调用方，其接收端每次看起来都是新的——这个决定权属于调用方。

## 测试

| 层 | 如何验证 |
|---|---|
| 协议解析与原语 | 单元测试，plist 与 wire 格式另有属性测试 |
| 控制面 | 向真实服务器开真实 TCP 连接的测试 |
| 媒体会话 | 驱动真实 UDP 套接字与真实 TCP 连接的测试 |
| 密钥流与计数器规则 | 与 UxPlay 自身 C 代码的差分测试 |
| 渲染边界 | 用假渲染器统计会话交付了什么 |
| GStreamer 后端 | 真实运行时，包含解码真机抓取的帧 |

差分测试最重要：它把"看起来对"变成"与被移植的那份实现一致"。媒体路径上两个严重缺陷，都是它（或它的存在）发现的。
